# 受控调度接线

本变更只增加控制层能力，合入不会自行启用调度、创建 socket、安装验证器或修改权限。
管理员完成下述准备后，才可在现有 `/etc/ai-brief-stage.json` 的 `live` 对象内设置
`"scheduler": true`。未设置时保持原运行方式。

## 固定边界

管理员维护 `/etc/ai-brief-scheduler.json`，使用与应用 `scheduled_runtime` 相同的五个字段：

```json
{
  "activation_date": "2026-11-04",
  "publisher_uid": 2001,
  "socket_path": "/run/ai-brief-scheduler/scheduled.sock",
  "node_path": "/opt/ai-brief-scheduler/node-v24.22.2/bin/node",
  "verifier_path": "/opt/ai-brief-scheduler/verifiers/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/scripts/verify-scheduled-delivery.mjs"
}
```

日期、UID 和提交 SHA 是示例，必须按批准的启用日期与实际身份填写。Publisher UID
必须与 relay UID 不同且均非 root。此文件及 Node、验证器完整依赖树由 root 所有，
文件和全部祖先不得由组或其他账号写入；配置应为 `0444`，运行时需要可读和目录可遍历。
依赖树来自固定 reports 提交，保留锁文件与安装验证记录。安装时物化包内符号链接；
控制层拒绝符号链接、硬链接、特殊文件和外部依赖路径。不得直接共享 Publisher 的可变工作目录。
Node 版本固定为 24.22.2；验证器树最多 20,000 个文件、512 MiB。

`/run/ai-brief-scheduler` 由 relay UID/GID 所有，权限恰为 `0711`。管理员配置对应的
tmpfiles 规则以在主机重启时恢复该目录，并确保目录创建早于容器启动。控制层只检查，
不创建目录或自动修正权限。`scheduled.sock` 由已审核运行时创建为 `0666`；
内核 `SO_PEERCRED` 在读取请求之前只允许指定的 Publisher UID。
不能复用只读回执检查器的目录或 socket。

容器仅新增四项挂载：配置、Node 文件、完整固定验证器树均只读，IPC 目录可写。
保留原 relay 独占锁、账本和同一个 WeCom 客户端。没有第二个发送服务、网络监听端口、
额外组、凭据、目标或任意程序参数。Publisher 使用固定安装的 `scheduled_client.py`，
`--socket` 指向上述路径，`--reader-uid` 为实际 relay UID；现有 systemd 限制保持有效。

## 安装与首次启用

1. 先完成控制代码审查及隔离验证。旧固定控制入口不会自动加载本次更新；需按已有管理员
   安装流程备份并升级完整控制模块，包含 `scheduler_service.py`。已安装版本化控制入口的
   环境由其现有 Git tree/CI 校验流程安装完整 `deploy/` 快照。不能仅覆盖应用容器命令。
2. 在批准的维护窗口只读检查历史原包、日期去重及所有未决写入。停止旧消费者并确认独占后，
   对原账本作一致性备份、记录哈希与属主，再执行已审核的历史日期迁移。迁移缺项、冲突或
   未知投递结果时停止，不恢复旧账本来消除阻断。
3. 安装固定 Node、验证器及客户端，准备 IPC 目录和 root 配置；在无凭据、无外部写入的隔离环境
   验证真实 Unix socket、跨 UID 鉴权、暂停、重启、去重和回滚。不得向正式群发探针。
4. 为一次新的受控应用发布显式启用 `live.scheduler`，并使 Publisher 激活日期一致。
   启动器在停旧服务前对候选版本和回滚版本分别执行无网络、无账本、无凭据挂载预检，
   检查调度 API、运行时配置、Node 版本和完整 JS 依赖导入。预检不准入、不发送。
   旧版本不兼容时拒绝切换，须先准备支持调度的回滚版本。
5. 通过原 pause/handoff/start-paused/activate 流程上线并核对健康。相同应用 SHA 的普通
   deploy 只检查健康，不是重新配置入口；不能靠修改配置后重复同一 SHA 来启用功能。
   首次启用必须协调到新的受控发布，或另行审核维护操作。

## CD、重启与回滚

若使用版本化控制入口，还必须由管理员更新固定的 `control_entry.py`，使其识别
退出码 `75` 与精确的 `deferred` 结果。该结果不宣称部署成功，恢复原控制器后保留
同一候选的重试资格；普通失败仍阻断，未知结果仍保留意图。仅下载候选 `deploy/`
快照不会升级正在执行的固定入口。停止前会在撤销重启授权后再次取得当前进程的暂停
确认，不能复用可能已重启进程的旧排空确认。

启用前，候选和回滚版本都必须支持 `SCHEDULER_DRAIN_VERSION = 1`。先在调度关闭时
发布包含此协议的应用，再为后续新发布启用调度；不能用缺少该协议的旧版本充当回滚目标。
`drain` 在 relay 同一事件循环内检查排空并暂停，未完成任务会使它明确拒绝且保持旧服务
活动、原重启授权不变。首次切换收到明确拒绝会撤销此次切换意图，之后可重新尝试；
响应丢失则保留切换记录并等待对账。成功暂停后才撤销重启授权并停止旧容器，停止后仍按
原独占锁交接账本。活动健康检查使用 `delivery_ready`，允许合法排队或冻结的未知任务
留在账本；部署交接仍要求严格的 `reconciled`，二者不互相替代。

配置、身份、Node 内容和整棵验证器树共同形成容器标签 `sfcloud.ai.scheduler-binding`。
健康检查核对标签、固定启动参数、挂载读写性、服务身份及隔离约束。应用重启使用同一个
容器配置；后续 CD 和应用回滚均从固定管理员配置重新生成相同接线。

已有调度容器的配置绑定改变或关闭开关时，受控切换在停旧服务前拒绝。
不能通过更换日期、验证器、客户端身份或删配置绕过持久化 scope；这些变化需要单独对账和维护。
控制层回滚同样必须保留支持此模块的版本；旧控制层没有这项能力，不能直接回滚到它。

所有未完成定时任务（含尚未到期、等待重试和未知结果）继续阻止部署排空。
回滚只恢复代码，不恢复账本、不清去重、不重发未知结果。启用后的首个正式日报真实回执
通过之前，只能报告接线与隔离测试结果，不能宣称端到端投递已成功。
