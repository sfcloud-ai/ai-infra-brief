# 晨报图文投递契约 v3.1

## 六主题交付与缺页接续（2026-11-13 起的当前要求）

本节是当前交付规则：与下文历史部分晨报、状态页或整期重发描述冲突时，以本节为准。六方向、十三来源组仍须逐一真实研究；不是只选两家引擎后把其余方向写成未完成。未就绪页不阻断其他已完整核验的页面，也不生成占位 URL 或把“尚未核验”单独包装成文章。

固定主题、顺序与稳定 article-id：

| 主题标题格式 | article-id | 必查内容 |
| --- | --- | --- |
| 模型服务与 GPU 超配：具体问题或进展 | model-serving-gpu | 独立权重、KV/运行状态、池化调度、多租户隔离、成本与 SLO |
| 硬件与算力平台：具体变化及适用条件 | hardware-status | GPU/异构硬件、通信/RDMA、存储路径；原始型号与实验条件 |
| 模型与架构：具体机制变化 | model-architecture-status | GLM/DeepSeek/Qwen 等模型卡及技术文章，MoE、状态/KV、引擎适配 |
| 制造业具身智能训练：具体训练方案或进展 | embodied-training | 训练论文/正文、数据与控制流程、实验机器人/任务、复现及工厂落地条件 |
| 前沿小模型：具体模型及质量成本边界 | small-model-status | 总权重与激活参数分开，任务质量、精度、延迟/吞吐、显存、硬件及实现 |
| 推理引擎每日变动：具体工程主题 | inference-engines | 同篇 vLLM、SGLang、DeepInfer 三小节；代码与博客分别核查 |

主题是必须研究的范围，不是必须凑出的六条新闻。每页正文依次包含：实际问题与例子；本次变化及原始日期/版本；核心机制与数据/控制流程；与现有实现区别；实验硬件、调优基线、负载、指标及限制；工程成熟度与复现条件；交付价值和下一步；原始来源与具体 PR/commit。适用时配原创机制图。完整核查确无合格新项，可简述实际检索窗口与结果；未查完不能写成无新项。

发现页/列表只是入口。发现相关候选后必须续读正文、PR 说明与实际 diff、论文和模型卡，核验日期、变更状态及后续 revert；有合理候选不得仅因已有其他栏目可发而停止。引擎 release 成功不等于 commits/PR 已覆盖。入口异常时记录实际失败，在既有权限下尝试官方网页/API/raw Git、论文或项目官网等能回答同一事实的可用入口；不得绕过明确权限拒绝，也不得将未尝试记作访问失败。

无法完成的主题记为待补页：保留原 report_date、主题/article-id、已完成范围、缺失证据、具体原因、原操作和检查点、下一动作及通知回执。公开晨报说明只写简短具体原因，不暴露私有诊断。待补页不进入 articles、导航、URL 清单和海报新闻分区，不创建“未完成”空正文来放行；已有真实页面不因新一轮缺口删除或改成空壳。

“下一轮”是下一次定时任务触发（例如下一小时的 :20），不是下一自然日。沿原日期、原检查点继续缺项，已成功研究/已发送页面不重做、不重发；跨日仍保留原日期，不阻止新日报独立启动。失败不等于放弃，未知上传/发送先按原操作对账。补页通过证据、审计、Pages 校验后，仅通知本轮新完成的页，记录页级发送回执；补齐前不宣称整期研究完成。

这是实际执行必须遵循的要求，不是声称现有服务已支持。固定旧计划和原失败不改写；需要新 schema、页级通知或宿主接续支持时，先按原授权完成兼容接入与验证，不手改已绑定字节、不虚构字段、不绕过校验，也不把 Prompt 合入说成补页已经投递。

长期文字格式为**本期每篇子文章的子标题及对应 Pages URL**，同一条顶层消息附**一张横版分区总海报**。不是整期一个主题标题，也不是逐篇另发多张图片。文字不另加各篇摘要；海报分区承载各篇的精简文字说明或架构说明；完整机制、实验条件、限制、来源和详细图解回到报告站阅读。此契约不授予发送、建仓库、改定时任务、部署或扩权的权限。

## 当前首发与下一小时补页通知格式

首发仅列本轮已发布且验证可用的页面；最后可有一段“晨报说明”，逐项说明缺页原因，不为缺页写 URL。这是“不追加摘要段”的明确例外，仍不写各篇摘要。示例：

```text
AI Infra 晨报 · YYYY-MM-DD

模型服务与 GPU 超配：已核实的具体主题
https://sfcloud-ai.github.io/ai-infra-reports/YYYY-MM-DD/model-serving-gpu/

晨报说明：制造业具身智能训练暂缺，论文实验条件仍待核验；下一次定时任务（下一小时 :20）继续补齐。
```

下轮只发送新增完成页，日期保持原报告日期，不重复首发已送达页面或借补页重发整期：

```text
AI Infra 晨报 · YYYY-MM-DD · 补充

制造业具身智能训练：补齐后的具体主题
https://sfcloud-ai.github.io/ai-infra-reports/YYYY-MM-DD/embodied-training/
```

补充的正文、图片、原日期、article-id、内容哈希、发布 commit 和真实分项回执必须绑定同一补页批次。并发/未知结果先对账；相同页及内容哈希已送达则跳过。首发横版海报只呈现已就绪内容；补充图片如由实际部署合同要求，必须对应本批新增页面，不重复原整期海报。现行发布器若只支持整期通知或短修订通知，应先完成并验证兼容接入；以上示例不是可直接绕过现役校验的命令。

## 顶层图文消息

首行使用 `AI Infra 晨报 · YYYY-MM-DD` 保留机器识别标识；空行后按 `report.json` 的 `articles` 原顺序列出每篇子标题，下一行只放该篇已核验的完整 URL，各篇间空一行。无编号、无 Markdown 列表标记，不追加摘要段。例：

```text
AI Infra 晨报 · YYYY-MM-DD

第一篇子标题
https://sfcloud-ai.github.io/ai-infra-reports/YYYY-MM-DD/first-article/

第二篇子标题
https://sfcloud-ai.github.io/ai-infra-reports/YYYY-MM-DD/second-article/
```

同一条顶层消息直接附一张 Slack 托管 PNG/JPEG 海报。原机器人路径使用 `file_share`；固定身份的 `notice_connector` 路径允许实际 history 不含 subtype，或为 `file_share`，不得补造字段。发布工具关闭链接/媒体 unfurl，不添加 section accessory 或额外 attachments。实际读取必须证实子标题、链接与原生附件可见，离线模板不能替代真实连接器结构验证。

文字经实际 relay 渲染后不超过 1,900 UTF-8 字节，使全部子标题与完整 URL 保持在一片中。过长应在发布前精简同一 report.json 中的标题，不截断 URL，不设计跨消息长文重组，不擅用第三方短链。

报告站使用独立仓库，每天只有一份当前网页：日期总页为 `/YYYY-MM-DD/`，子文章为 `/YYYY-MM-DD/<article-id>/`，公开图片为 `/reports/YYYY-MM-DD/assets/<name>`。对外链接、canonical、站内导航、搜索结果和新通知正文不含 `/rN/` 版本段，不在界面展示“修订版”。引擎动态按真实内容组织，不为了栏目制造空文章；消息直接链接每篇子文章，不必额外放日期总页。网页修正后仍使用相同日期和文章入口，不复制一套版本网页。

旧 `/YYYY-MM-DD/rN/` 及其文章 URL 只保留兼容跳转，不保留旧正文；仍存在的文章跳到相同 article-id 的稳定 URL，已移除文章跳到该日期总页。跳转壳使用 noindex 和稳定 canonical，不进入导航或搜索。未知日期、非法路径不得被通配跳转伪装成有效页面。Git 历史和原发布证据继续保存；公开网页合一不表示删除发送记录或覆盖已绑定原包。

`revision`、`request_id`、原文件哈希、提交和发送账本仍是内部发布与去重身份，不能从无版本的公开 URL 推导或重置它们。报告、子文章、图片与去重索引必须对应同一获准内容；网页哈希、内部 revision 增加或 URL 迁移本身不决定重发；经内容审查的 `schema_version: "1.1"` 与 `revision_notice` 按下述修订策略产生独立通知。

## 发布先于通知

1. 完整内容经过证据、隐私和公开范围审查，在指定报告仓库合入。Git 合入不等于 Pages 上线。
2. 站点构建、发布成功，记录发布 commit、内部报告版本和稳定规范 URL；实际读取日期总页、子文章、图片、根 publication.json 及当前报告源/清单，核对实际内容、哈希与同一发布提交。迁移时还须实际验证旧版本 URL 跳到正确稳定入口，且导航和搜索只出现当前内容。HTTP 成功状态、空页面、登录页或错误页都不能单独作为验证依据；访问范围须适合消息接收者。
3. 只有上述验证成功，已获授权的通知步骤才可发送。发布失败、链接未验证、版本不符或访问范围不明时，停留在待发布状态并报告具体失败，不假称链接可用。
4. Pages 首次上线前，既有完整正文仅作明确选择的过渡兜底，主要内容不得再次藏在线程 MD。兜底不固化为长期标准，不增加长期分段协议，也不自动改当前调度。上线后临时故障默认暂停通知；不能未经核对另发同一期的“成功”消息。

## 海报承载信息

一张横版总海报按本期子文章分区，用少量可读文字概括关键机制、判断或架构关系，不是装饰图。不把密集技术笔记拼成长图，不用绿色整页底色。保留影响判断的条件；不同模型独立权重。没有可靠数值时画结构说明，不编造性能柱状图。完整证据和限制放在对应子文章，海报与站内报告版本一致。

只接受消息自身 `files` 中的一张 PNG/JPEG，最多 2,000,000 字节，满足实际 `images.validate_file` 对 MIME、filetype、工作区、文件 ID、访问模式和可信下载地址的校验。SVG 须先栅格化并检查移动端可读性。网页预览、文件链接、Block Kit image、线程图片、无合格标题的独立图或后补附件不能替代原生海报。

上传/共享后读取实际消息：上传工具的身份可能不等于固定发送者。现有 `forward_images` 和 `files:read` 必须已经有效；格式变更不等于开启权限。工具不能形成合格顶层图文事件时，明确报告不支持，不伪造文件 ID 或回执。

## 校验、回执与去重

- Slack：从已认证工作区和固定目的地读取消息，核对 sender、顶层、未编辑、规范标题、完整 URL 和单张附件 ID。支持的 blocks 必须包含相同可见正文；fallback 有 URL 而 blocks 仅有摘要或不可验证控件时，不能宣称可见内容合格。
- 本仓库的 `prepare_article_notice_preview`、`prepare_notice_preview` 和旧原生 `check_received_notice` 保留历史版本 URL 的默认契约，不是新稳定 URL 发布能力。定时链路显式构建并校验稳定 manifest，历史已绑定通知仍按原版次、原字节和原账本验证，不将旧意图改写为稳定 URL。新日报使用已经部署并验证的报告仓库发布器与 scheduled_delivery 路径，不能通过手改旧模板、清单或已绑定字节绕过校验；实际部署尚不支持稳定路径时报告具体阻断，不退回生成新版本网页。离线模板始终为`delivery_allowed=false`、`publication_status=not_checked`；不访问 Pages、不上传图片，也不是 Slack API 参数。历史校验仍须提供实际认证得到的 `read_context={channel_id, team_id}`，已有 channel/team 字段必须一致。
- 核对历史原生连接器时，向 `check_received_notice` 传入与部署状态一致的 `notice_connector`：精确用户、App、工具归属、报告站根 URL 和启用截止游标。实际用户、App、无 bot_id、未编辑顶层消息、可见正文与回退文字、归属块、同一期全部文章 URL 及单张附件所有者均须通过校验。分项标题、顺序、数量及 URL 逐项匹配同源构建的 notice.json，不仅检查域名。工具自动加入归属，调用方不手动补写。只有通过全部校验才从企微正文移除工具归属。配置和结构细节见 `integrations/slack_wecom/NOTICE_CONNECTOR.md`；未启用该配置不能假定连接器消息会被转发。
- 新报告的当前源使用 `reports/YYYY-MM-DD/` 下的 report.json、articles 和 assets；从相同源生成稳定 `/reports/YYYY-MM-DD/notice.json` 与发布证明。内部 `/reports/YYYY-MM-DD/rN/notice.json`、publication-proof.json 可按已部署协议保留为当前证据的技术别名，不能因此生成第二套网页或版本化公开文章链接。绑定正文、文章清单、原报告和海报 SHA256、构建 commit；历史原包及旧回执不改写。转发器只读配置中固定的报告站，证据读取禁止重定向且不携带 Slack 凭据，前后读取 publication.json 核对 commit；访问失败保留消息和游标，不能当成非法消息跳过。网页兼容跳转不放宽机器证据读取规则。清单读取设总期限，未知写入仍禁止自动重发。
- 校验返回真实 Slack ts 与 `auto:<ts>`，始终保留 `wecom_status=not_checked`、`publication_status=not_checked`。标题匹配、附件元数据通过、离线假传输成功均不代表企微送达或网页可访问。
- 企微：已有权限的执行者核对对应 relay 请求的文字和图片状态，文字 `parts_sent == parts_total`、海报为 `sent`；再在获准目的地检查可见内容、顺序和图中文字。缺回执、`partial`、`failed`、`unknown` 均不算完整成功。
- 通知账本继续关联内部报告版本、原 request_id、发布 commit、海报摘要、目的地与真实 Slack ts，保留原日期和版次去重关系；历史连接器的原版次 URL 映射与原机器人源消息去重记录不重置。同一期换 ts、附件 ID、网页路径或内部版本都不重置原发送意图。同日重要修订使用新 rN 请求，按经过审查的 `revision_notice` 发送短文，普通维护以网页更新结束。未知结果先核对已有回执，不自动重发、补发历史，不靠编辑旧消息期待补转发。

## 责任边界

云端任务读取同一 commit 的研究、编辑及本契约；本地应用的演练仍是 mock runner；Slack 发布工具、relay、报告仓库机器人和 Pages 发布是独立步骤。更新契约不会自行修改定时任务、生产服务或权限，也不把离线模板接成真实发布器。真实 Slack→企微联调须在明确授权的测试范围进行。

回归采用合成消息、合成图片和假传输，验证标题、blocks、URL、精确身份、图片计划、版次与源消息去重。报告站和机器人在独立报告仓库接入。relay 继续使用原 SQLite 账本并保存独立连接器身份摘要与版次映射；原时间戳来源键兼容旧版。启用时保留游标与历史，不重置投递状态。

分项通知海报采用原字节契约：上传前核对本地实际字节的 SHA256 与已发布 manifest 一致，并使用已验证不会改写字节的原生上传路径。正式生产路径未经实测不能宣称支持；不得以像素相同替代字节摘要。历史原生连接器读回后必须下载该实际 file ID 的原图字节并传给 `check_received_notice`，不符则停止并核对，不能换 file ID 重发。企微转发器必须在任何文字发送前先验证海报，复用同一份已验字节；partial/unknown 不得报成功。

## 同日修订通知

首次发布继续使用完整标题列表和原海报。首次通知后，事实纠错 `correction` 或重要新增 `material_update` 发送一条日期、简短说明与稳定日期页链接；排版、链接维护与措辞调整 `maintenance` 更新网页，记录 `web_only / skipped` 零发送。说明非空单行，最多 600 UTF-8 字节，概括首次发布以来仍有效的重要变化。完整修订包使用 `schema_version: "1.1"`、递增 revision 和新 `morning-YYYYMMDD-rN`，由原 Publisher→scheduler→relay 执行；首次尚未发送时最新版本仍承担完整首发。已进入发送边界的原请求与未知回执保留，后续请求不重复尝试未知的同一文字。编辑与接入细节见同 commit 的 [editor.md](editor.md#同日修订与通知)。
