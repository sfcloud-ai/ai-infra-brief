# 修订通知队列

正式规则见 [报告仓库同日修订通知](https://github.com/sfcloud-ai/ai-infra-reports/blob/main/docs/revision-notifications.md)。报告的 1.1 格式携带经过内容审查的类别和短说明；可信 Node verifier 验证原包、不可变来源与当前 Pages 后输出计划。本机请求没有目的地、任意命令或调用方 verified 标记。

`scheduled_revision_notices` 保存原计划、原包、原海报、实际通知角色及覆盖关系；`scheduled_supersessions` 保存原请求被接续前的记录哈希和分片状态。它们位于原 relay SQLite，操作回执仍使用原 `requests`、`parts`、`image_parts`。报告正文和历史继续保存在 Git，初版 `scheduled_notices`、日期声明及已发送回执保留。

发送角色有三种：`initial` 使用完整标题列表与原海报；`revision_update` 使用一条短文字；`web_only` 以 `skipped` 结束并记录零发送。版本去重使用日期和 revision，重复请求还必须匹配原包及提交。首次尚未发送的版本可以由最新已核验版本接续，保留原状态并取消旧验证租约。首次已有分片发送时，重要修订使用独立文字请求；旧未知意图保持冻结。

连续修订合并确认未发送的重要通知时记录原请求与哈希，maintenance 保留待发的重要说明。发送中或结果未知的相同文字不会通过新版本再次尝试；已确认成功后，新重要修订可使用独立通知。发送与接续使用同一事务边界，验证后重新确认 owner；确切失败继续受共享限速和退避约束，未知不重试。启动对账和日期检查识别完整绑定的未知修订，其他孤儿未知仍要求对账。

部署须配套更新 relay 构建、固定 Node verifier 和宿主机 `scheduled_client.py`，保留原配置身份、私有数据库及原回执；候选和回滚版本都运行原 CD 预检。生产启用前在隔离原库副本检查新增表和历史兼容。接续正在发送的工作时保留原发送边界；不使用生产消息来填补隔离测试覆盖率。

可信部署控制器在只读原账本发现修订记录时，要求候选/回滚运行时声明修订能力，并在停机后、可写账本挂载前再次检查。旧版本会提前拒绝；回滚须选兼容版本，或保持当前版本修复，不能删除原记录以绕过门槛。
