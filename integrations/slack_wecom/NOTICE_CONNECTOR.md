# 固定连接器通知

可选的 `notice_connector` 配置只接纳一个已验证、经用户授权的 App。
保留既有 `sender_id` 和目的会话，原机器人投递继续可用。身份不能从显示名称推断；
上线前应在私有测试频道观察经过认证读取的原始历史，不能向正式收件人发送测试通知。

```json
{
  "user_id": "UOWNER",
  "app_id": "ACONNECTOR",
  "attribution_text": "*Send tool* <@UTOOL>",
  "report_base_url": "https://example.org/reports/",
  "not_before": "1700000000.000000"
}
```

同时启用 `forward_images`。配置用户必须等于读取器认证的 `user_id`，且不同于原发送者。
App 和归属文字必须来自实际观察；上例均为合成值。`not_before` 使用完成核对的启用游标。
数据库保存配置摘要，启用后拒绝静默修改或移除此身份。

通知为一条未经编辑的顶层消息：`AI Infra 晨报 · YYYY-MM-DD · 子标题`，空行后跟永久网址
`YYYY-MM-DD/rN/`，附一张属于固定用户和 workspace 的托管 PNG/JPEG。
可见富文本、回退正文、工具归属、完整链接目标和标签必须一致；允许 Slack 的标准实体转义。
只有验证成功才移除归属文字。图片继续经过现有受限认证下载和二进制格式检查。
此校验只证明身份和格式，不能证明报告事实或上线状态；发送前仍须访问实际公开网页。

同一版次网址即使使用新时间戳、新附件 ID 重发，也共享来源标识。
成功或结果未知的投递不会自动重发。明确的新 `rN` 版次是独立通知。
原时间戳来源键保持旧版格式，版次映射与请求原子记录；编辑或回退旧版均不能绕过原投递记录。

## 受控部署

1. 对最终提交执行完整 Linux 工作流及私有审查。
2. 备份并将该提交的 `resume.py` 安装到现有 root 管理的控制代码目录，保留所有者和权限。
   它通过功能检测兼容旧应用，同时允许新应用规范化正文并按版次去重。
3. 通过已有受控 CD 部署应用，此时仍不加入可选配置，保留旧版本及回退配置。
4. 核对所有待定和未知投递，经既有控制协议暂停、排空；保留游标与账本，再加入配置并
   通过同一协议启动已审查版本。不得重置游标或并行运行第二个转发器。核验就绪和身份绑定。

回退到不认识此配置的旧应用前，必须恢复启用前的配置。账本应保留，旧应用会忽略新增元数据键。
再次启用新配置时必须匹配已保存摘要。迁移身份必须另行核对，不能借修改配置静默授权其他发送者。

`check_received_notice(..., notice_connector=profile)` 将原始 Slack 消息与计划的正文和附件 ID
比较，仍返回 `wecom_status=not_checked`、`publication_status=not_checked`；真实转发回执和公开网页
证据须分别取得。
